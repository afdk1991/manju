# 扩展机制整合方案 · 五类扩展机制与方案A 三条主线的整合

> **定位**：本文件是《方案A（全栈效率优先）：个人主导 + 按需外包 + 分布式多人评审 落地方案》的**补充章节**（建议编号「七、扩展机制整合」），与 `docs/方案A落地总纲（项目007适配版）.md` 并列使用。
> 生成时间：2026-10-03 · 适用环境：WorkBuddy（插件 / 工作伙伴 / 专家 / 技能 / 连接器 五类机制）
> 与 `docs/TRAE_能力扩展方案.md` 的关系：那份覆盖 **TRAE CN**（另一套生态，103 插件、项目 MCP 目录 `~/.trae-cn/mcps/`），本份覆盖 **WorkBuddy** 的五类机制。**二者配置项位置完全不同，不要混用路径。**
> 术语沿用方案A 原文：自主开发 / 按需外包 / 分布式多人评审、五节点评审、绝不外包红线、T1~T8 发包清单。

---

## 0. 为什么方案A 需要这一章

方案A 的核心原则第 4 条「评审保质量」要求每个节点由「外部专业人员 + 自动化工具 + 目标用户」三方参与。其中「自动化工具」一环此前只落地为 CI 脚本（`.github/workflows/review-gates.yml` 四个 job）。

AI 侧五类扩展机制是这一环的**能力放大器**：它们能把「产品顾问 / 架构顾问 / 交叉评审员 / 测试工程师 / 合规顾问」这些外部角色，**部分前移**为可复现、可留痕、低成本的机检环节 —— 但**永远不能替代真人评审**（见 §4.1 红线 1）。

三条主线与五类机制的承接关系：

| 方案A 主线 | 主要承接机制 | 承接方式 |
|---|---|---|
| **个人主导开发** | 技能 + 连接器 + 工作伙伴 | 技能固化 SOP（改完必跑什么）、连接器打通外部系统、工作伙伴并行跑长链路任务 |
| **按需外包派单** | 技能 + 插件 + 工作伙伴 | 技能套任务书模板、插件做发包与文档沉淀、工作伙伴做交付前的脱敏打包 |
| **分布式多人评审** | 专家 + 工作伙伴 + 插件 + 连接器 | 专家提供评审视角、工作伙伴做对抗式复核、插件/连接器取 CI 与 PR 真实数据 |

## 1. 五类机制的用途定位、启用配置与适用任务

### 1.0 一句话区分（按层级从底到顶）

| 层级 | 机制 | 本质 |
|---|---|---|
| 协议层 | **连接器（Connector / MCP）** | 给模型接上外部系统的「手」，本质是工具通道 |
| 包层 | **插件（Plugin）** | 市场安装的能力包，一个插件可同时落地出技能、命令与 MCP 配置，并带授权引导 |
| 方法层 | **技能（Skills）** | `SKILL.md` 描述的 SOP 与领域知识，告诉模型「这件事该怎么做」 |
| 角色层 | **专家（Expert）** | 固定的专业视角与方法论，决定模型「以什么身份、按什么标准判断」 |
| 执行层 | **工作伙伴（Agent / 子代理）** | 独立上下文的执行单元，决定「谁去做、能否并行、能否隔离」 |

---

### 1.1 插件（Plugin）

**用途定位**：把外部产品/平台（GitHub、腾讯文档、企业 IM、各类 SaaS、设计工具等）包装成「开箱即用」的能力包。插件安装后通常自带若干技能（SKILL.md）与工具，直接出现在可用技能列表里。

**启用与配置（配置项及存放位置，本机实测）**

| 配置项 | 存放位置 |
|---|---|
| 插件安装清单 | `C:\Users\addk1\.workbuddy\plugins\installed_plugins.json`（键格式 `名称@市场源`，记录 `scope` / `installPath` / `version` / `installedAt` / `lastUpdated`） |
| 插件实体目录 | `C:\Users\addk1\.workbuddy\plugins\cache\<市场源>\<插件名>\<版本>\` |
| 市场源 | `codebuddy-plugins-official`、`workbuddy-builtin`、`workbuddy-connector-plugins-official`、`cb_teams_marketplace`、`experts`、`my-experts`（登记于 `known_marketplaces.json` 与 `marketplaces\`） |
| 授权 / 启用状态 | `~/.workbuddy/plugin-account-state\`、`plugin-marketplace-state-new`、`plugin-status-daily.json`；状态分 **bound（已授权）** 与 **enabled（已开启）** 两态，二者不等价 |
| 插件自带的技能 | 插件目录内 `skills/<name>/SKILL.md`，例如 `...\workbuddy-connector-plugins-official\github\...\skills\github\SKILL.md` |

**启用方式**：聊天窗口左下角「+」菜单 / 连接器管理页启用；查看用 `list_installed_plugins`；发现候选用 `search_plugins`（只读搜索）+ 推荐卡片；卸载用 `uninstall_plugin`（须传精确名称）。

**适合承担的任务**：文档/表格/演示稿的产出与同步、代码托管与 CI 交互、IM 通知与催办、设计素材与网盘备份。

**不适合**：核心业务逻辑实现；任何需要持有密钥的写操作（插件凭证由插件自行保管，对用户不透明）。

---

### 1.2 工作伙伴（Agent / 子代理）

**用途定位**：把长链路、可并行的任务交给**独立上下文**的执行单元；或组建团队分工（如 pm / fe-dev / reviewer），通过共享任务列表协同。

**启用与配置（无独立配置文件，全部由运行时参数决定）**

| 配置项 | 说明 / 存放位置 |
|---|---|
| 类型 `subagent_type` | 本环境可用：`general-purpose`（全工具）/ `Explore`（只读勘查）/ `Plan`（只读规划）/ `statusline-setup`，以及领域子代理（表格处理、文档创作/排版/格式转换等） |
| 权限模式 `mode` | `default` / `acceptEdits` / `bypassPermissions` / `plan`（plan 模式需计划审批） |
| 并发与隔离 | `run_in_background`（后台并行）、`name`（可寻址，便于点对点通信）、`max_turns`（回合上限，防失控） |
| 团队编排 | 团队目录 `~/.workbuddy\teams\`；消息走点对点 / 广播 / 关停请求三类 |
| 共享任务 | `~/.workbuddy\tasks\` + 共享任务列表（所有成员可见同一份，按 ID 顺序认领） |
| 结果回传 | 子代理结果**只回传给调用者，不直接给用户**；需要产出就明确令其落盘文件 |

**适合承担的任务**：大范围代码勘查（Explore，成本低）、长链路构建/发布编排、三条主线的并行推进（一边写需求文档、一边做技术预研）、**对抗式复核**（另起一个 Agent 只挑刺不改代码）。

**不适合**：需要最终决策权的动作（合入、发布、付款）；需要长期记忆的任务 —— **子代理不继承会话记忆，派发时必须把上下文写全**。

---

### 1.3 专家（Expert）

**用途定位**：提供稳定的专业视角与方法论，是「评审保质量」主线中最接近方案A 里外部顾问的一环。

**启用与配置**

| 配置项 | 存放位置 |
|---|---|
| 选用入口 | 左侧栏「专家」→ 专家中心按分类浏览并启用 |
| 专家包实体 | `C:\Users\addk1\.workbuddy\plugins\cache\experts\`、`my-experts\` |
| 自定义专家 | `C:\Users\addk1\.workbuddy\experts\custom\<用户ID>\` |
| 生命周期管理 | 走 `expert-manager` 技能（创建 / 转化 / 编辑 / 评审专家包） |
| **硬约束** | 同一会话**只能启用一个专家或一个专家团队**；已启用专家时不再推荐其它专家 |

**适合承担的任务**：需求评审（产品视角）、技术方案评审（架构视角）、测试用例设计、合规评审（法务/合规视角）。

**不适合**：跨领域同时启用多个（会冲突）；**不能替代**持证或需签字担责的真人顾问（方案A 的合规顾问、平台上架专员必须是真人）。

---

### 1.4 技能（Skills）

**用途定位**：把可复用的 SOP、领域知识、配套脚本固化成**按需加载**的指令包。是「个人主导开发」主线里最值得沉淀的资产 —— 一次写对，长期复用。

**启用与配置**

| 配置项 | 存放位置 |
|---|---|
| 用户级技能（跨项目） | `C:\Users\addk1\.workbuddy\skills\<技能名>\SKILL.md`（市场安装的带 `__skillhub` 后缀） |
| **项目级技能** | `<工作区>\.workbuddy\skills\<技能名>\SKILL.md` —— ⚠️ **本项目工作区当前尚未建立，建议补（见 §5）** |
| 随包资源 | 技能目录下的 `scripts\`、`references\`、`assets\` |
| 调用 | 按名调用；也可由模型按描述自动匹配（命中即加载正文） |
| 安装 / 禁用 | `search_and_install_skills`（先搜后装）、`skill_management`（列表与禁用） |
| **安全审计** | 安装新技能**必须先过 skills-security-check**（P0 / P1 / P2 分级）。用户级目录已有 200+ 个技能（跨项目共享），新增前务必走这一步 |

**适合承担的任务**：重复流程（内容再生成、构建冒烟、部署、评审记录生成）、领域规范（Office 文档、前端规范、地图与位置服务）、外包任务书与评审模板的模板化产出。

**不适合**：一次性临时任务（直接写脚本更快）；含密钥的逻辑（技能目录可能被云端同步，绝不能写 `keys/` 内容）。

---

### 1.5 连接器类扩展（Connector / MCP）

**用途定位**：模型与外部系统之间的**协议级**通道。两类承载：远程型（`url` + 授权头）与本地进程型（`command` + `args`，等价在本机起一个子进程）。

**启用与配置**

| 配置项 | 存放位置 |
|---|---|
| **本机实际生效配置** | `C:\Users\addk1\.workbuddy\connectors\default\mcp.json` → `mcpServers`（实测，server 名形如 `connector:github`） |
| 官方指引位置 | `~/.workbuddy/mcp.json`（⚠️ **不是** `~/.workbuddy/.mcp.json`）；本机该文件**尚不存在**，新增前先确认哪一份生效 |
| 远程型字段 | `url`、`type`、`timeout`、`headers` / `staticHeaders` |
| 本地型字段 | `command`、`args`、`runtime`、`staticEnv` |
| 开关与裁剪 | `disabled`（整关）、`disabledTools`（关掉个别高危工具） |
| 审批态 | `~/.workbuddy/mcp-approvals.json`；工具清单 `mcp-tool-list.json` |
| **启用动作** | 新增后必须在连接器管理页的「自定义连接器」入口点 **Trust** 才生效 |

**适合承担的任务**：必须联网取真实数据的环节 —— 部署（EdgeOne Makers）、代码托管与 CI 读数（GitHub）、邮件收发（Agent Mail）、文档/表格读写、地图与金融数据等。

**不适合**：本地文件就能完成的任务（白付一次协议开销）；以及任何会把 `keys/`、`.env`、token 暴露出去的对接。

### 1.6 五类机制横向对比

| 维度 | 插件 | 工作伙伴 | 专家 | 技能 | 连接器(MCP) |
|---|---|---|---|---|---|
| 层级 | 包层 | 执行层 | 角色层 | 方法层 | 协议层 |
| 生命周期 | 长期安装 | 单次任务 | 单次会话 | 长期安装 | 长期配置 |
| 是否落盘 | ✅ 安装清单 | ⚠️ 仅团队/任务目录 | ✅ 专家目录 | ✅ 技能目录 | ✅ mcp.json |
| 是否需授权 | 多数需要（bound） | 不需要 | 不需要 | 不需要 | 需要（Trust / Token） |
| 消耗外部配额 | 视插件 | 否 | 否 | 否 | ✅ 多数据计费/限流 |
| 上下文占用 | 中 | 低（独立上下文） | 中（常驻提示） | 按需加载 | **高**（工具定义全量注入） |
| 能否并行 | 否 | ✅ 可后台并行 | 否 | 否 | 否 |
| 主要风险 | 凭证不透明 | 越权 / 回合失控 | 角色冲突 | 供应链安全 | 权限外泄 |

## 2. 协同关系表

### 2.1 调用矩阵（行 = 调用方，列 = 被调用方）

| 调用方 ＼ 被调用 | 插件 | 工作伙伴 | 专家 | 技能 | 连接器(MCP) |
|---|---|---|---|---|---|
| **主会话（你 / 我）** | ✅ 启用、查看、卸载 | ✅ 派发、命名、后台运行 | ✅ 选一个启用 | ✅ 按名调用 | ✅ 配置 + Trust |
| 插件 | — | ○ 少数插件自带子代理 | ○ 专家类插件 | ✅ 落地为技能 | ✅ 注册 MCP server |
| 工作伙伴 | ○ 可用父会话工具 | ✅ 团队内互发消息 | ❌ 不可自行换专家 | ✅ 可自行加载技能 | ○ 继承父会话可用工具 |
| 专家 | ○ 可建议安装 | ○ 可建议派发 | ❌ 互斥 | ✅ 通常绑定一组技能 | ○ 可建议连接 |
| 技能 | ○ 可指导安装 | ○ 可指导编排 | ❌ 不可 | ✅ 可引用其它技能 | ✅ 可要求连接某 MCP |
| 连接器(MCP) | — | — | — | — | —（终止层） |

> ✅ = 直接支持　○ = 间接 / 受限　❌ = 不支持或禁止

### 2.2 发现 · 上下文传递 · 权限边界 · 依赖关系

| 机制 | 如何被「发现」 | 上下文如何传入 | 上下文如何传出 | 权限边界 | 上游依赖 |
|---|---|---|---|---|---|
| 插件 | 连接器管理页 / 只读搜索后推荐 | 安装后自动进入可用列表，描述被模型读取 | 通过它提供的工具返回值 | 插件自带授权，**凭证对用户不透明** | 市场源、账号授权 |
| 工作伙伴 | 主会话显式派发 | **只靠派发时写的 prompt**（不继承会话记忆，必须写全路径、红线、判据） | 仅回传给调用者；需产出则令其落盘文件 | 由 `mode` 决定；全工具集等价主会话权限 | 主会话、共享任务列表 |
| 专家 | 专家中心选择 / 推荐 | 常驻系统提示（角色设定 + 方法论） | 通过回复与产出文档 | 只影响判断口径，**不额外获得工具** | 无（但同会话只能一个） |
| 技能 | 按名调用 / 描述自动匹配 | `SKILL.md` 正文 + `references/` 按需读取 | 产出文件 / 命令结果 | 受当前沙箱与工具白名单约束 | 可能依赖某个 MCP 或 CLI |
| 连接器(MCP) | 管理页 Trust / `mcpServers` 配置 | 工具名 + 参数 schema（**全量注入上下文**） | 工具返回值（JSON / 文本） | **Trust 后即拥有该 server 全部工具**；本地型等价本机用户权限 | 凭证、网络、runtime |

**三条关键约束**

1. **上下文不做隐式继承** —— 工作伙伴不会自动拿到主会话记忆；技能不会自动拿到其它技能的输出；每次交接都必须显式落盘或用消息传递。
2. **权限不做自动收敛** —— MCP 一旦 Trust，其全部工具即进入可用集（只能用 `disabledTools` 裁剪）；本地型 MCP 以本机用户权限运行，**等价在你机器上开了一个 shell**。
3. **专家互斥** —— 一个会话只能启用一个专家 / 专家团队；跨评审节点换视角需要先结束当前专家或另起会话。

|---|---|---|

## 3. 五阶段介入时机与职责（需求 → 开发 → 外包交接 → 评审 → 交付）

### 3.0 阶段 × 机制总览

|---|---|---|---|---|---|
| 插件 | ○ | ✅ | ✅ | ✅ | ✅ |
| 工作伙伴 | ○ | ✅ | ○ | ✅ | ○ |
| 专家 | ✅ | ○ | — | ✅ | ○ |
| 技能 | ✅ | ✅ | ✅ | ✅ | ✅ |
| 连接器(MCP) | ○ | ✅ | ○ | ✅ | ✅ |

> ✅ = 该阶段主承担　○ = 辅助介入　— = 不介入

---

### 3.1 ① 需求阶段

| 机制 | 介入时机 | 具体职责 |
|---|---|---|
| **专家** | 需求清单成形后、发外部评审前 | 选定产品 / 业务视角专家，对 PRD 与功能清单做逻辑完整性、可行性预判，产出「需求评审意见表」初稿 —— 对应方案A 需求评审中「外部产品顾问」的**机检前置** |
| **技能** | 写 PRD 时 | 调用文档/模板类技能产出 PRD 骨架与 `review/01-需求评审记录.md` 初稿，保证字段与评审清单对齐 |
| **工作伙伴** | 需求评审前 | 派 `Explore` 子代理勘查仓库现状，确认需求是否建立在**过期事实**上（本项目 `docs/SDK_状态.md` 曾因工具链结论过期导致误判「四端都构建不了」，这类错误必须在需求阶段拦掉） |
| **插件 / 连接器** | 文档协同时 | 文档类插件沉淀需求文档；GitHub 读取历史 issue / PR 作为需求来源 |

**主线落点**：个人主导（核心业务流程自己定义）+ 评审（机检前置，降低外部顾问的返工成本）。

### 3.2 ② 开发阶段

| 机制 | 介入时机 | 具体职责 |
|---|---|---|

## 4. 启用后的限制、冲突处理与风险注意事项

### 4.1 能力边界（红线，🔴 为硬约束）

| # | 限制 | 说明与处置 |
|---|---|---|
| 1 | 🔴 **机制不替代真人评审** | 方案A 的「外部专业人员 + 目标用户」是真人。专家 / Agent 只能做机检前置；合规签字、法律责任、平台上架终审必须由真人完成 |
| 2 | 🔴 **准出判据唯一** | 准出只看 CI 门禁（`review-gates.yml`）+ `review/` 五份记录。专家意见不作为准出依据，只能转成整改项 |
| 3 | 🔴 **密钥一律不外泄** | `keys/*.pem`、`.env`、MCP token、GH Secret 不得写入任何技能、任务书、评审记录；本地型 MCP 不得挂载 `keys/`、`.ssh/` 目录 |
| 4 | 🟡 专家互斥 | 同一会话一个专家 / 专家团队；跨节点换视角需结束当前专家或另起会话 |
| 5 | 🟡 子代理无记忆 | 派发时必须写全：绝对路径、红线、判据、产出文件路径、回合上限 |
| 6 | 🟡 上下文膨胀 | 连接器 / 插件全量启用会把大量工具定义注入上下文。按阶段启用，不用即关（`disabled` 或关闭插件） |
| 7 | 🟡 文档内不写 PEM 字面量 | CI 的 security-gates 会扫描私钥头；写评审记录与技能时避免完整 PEM 头（本项目已因此踩过门禁红） |

### 4.2 冲突处理规则（按序执行）

| 冲突场景 | 处理顺序 |
|---|---|
| 同一能力有多个来源（如 GitHub 既有插件技能、又有 `connector:github` MCP） | **固定一条通道**：评审与 CI 走 GitHub 工具、部署走 Makers 连接器；另一条关掉，避免重复调用与上下文浪费 |
| 插件自带技能与用户级技能同名 | 市场安装带 `__skillhub` 后缀已规避大部分；若仍冲突，用 `skill_management` 禁用其一后复测 |
| 技能与专家方法论矛盾 | **以专家口径为准**（角色层高于方法层），并把差异写进评审记录备查 |
| 专家意见与外包交付物冲突 | **以任务书验收标准为准**（`docs/外包任务说明书与验收标准.md` §4），专家意见作为整改项而非拒收理由 |
| 两个 Agent 并发写同一文件 | 禁止并发写；先落盘再合并。本项目 `makers/static/` 是构建产物目录（`emptyOutDir` 会清空），并发写必丢 |
| MCP 工具与本地脚本功能重复 | **优先本地脚本**（可进 CI、可复现、可审计）；MCP 只用于「必须联网取真实数据」的环节 |

### 4.3 建议并入 `docs/风险台账.md` 的新增风险项

| # | 风险 | 触发条件 | 预案 | 等级 |
|---|---|---|---|---|
| R-A | **供应链安全**：新装技能 / 插件含恶意脚本 | 来源不可信或未审计 | 安装前强制 skills-security-check；P0 不装、P1 需人工确认、P2 正常装 | 🔴 |
| R-B | **权限外泄**：本地型 MCP 等价本机 shell | MCP 进程被授予 Trust | 只 Trust 官方 / 自建 server；用 `disabledTools` 裁剪高危工具；不挂载 `keys/`、`.ssh/` | 🔴 |
| R-C | **评审幻觉**：专家 / Agent 给出「看着专业实则错误」的结论 | 用其结论做准出判断 | 准出只看 CI + 记录；专家意见必须落到可复核条目 | 🔴 |
| R-D | **上下文膨胀**：有效指令被工具定义挤掉 | 连接器 / 插件启用过多 | 按阶段启用；每季度清理一次清单 | 🟡 |
| R-E | **版本漂移**：插件 / 技能自动更新改变行为 | `lastUpdated` 变化 | 记录版本与 installedAt；关键链路锁版 + 冒烟复跑 | 🟡 |
| R-F | **成本与配额**：MCP 调用计费 / 限流 | 高频轮询式调用 | 批量而非轮询；结果落盘复用 | 🟡 |
| R-G | **凭据散落**：`connectors/default/mcp.json` 与指引的 `~/.workbuddy/mcp.json` 两份并存 | 新增 server 写错文件 | 新增前先确认生效文件；配置只存本地，**绝不入库** | 🟡 |

### 4.4 与方案A 六章的一致性说明

- 本章**不改动**技术栈裁决 —— 项目007 仍以现状为准（Flutter 主干 + FastAPI + SQLite + EdgeOne Serverless + Vite/React/TS Web），方案A 的 UniApp / NestJS / MySQL / Redis / Docker 一律不采用，论证见 `docs/鸿蒙取舍与方案A可行性对比评估.md`。
