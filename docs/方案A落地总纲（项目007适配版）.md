## 1. 技术栈裁决（方案A 原文 vs 项目007 现状）

**裁决原则**：方案A 的**治理骨架全盘采用**，技术栈**以项目007 现状为准**。
理由：项目007 需覆盖 **Android / iOS / HarmonyOS / Windows / macOS / Linux 六端**，
方案A 的 UniApp 组合无法覆盖鸿蒙；且第一期 Web 站（Vite+React+TS）已上线验证，推翻不划算。
完整论证见 `docs/鸿蒙取舍与方案A可行性对比评估.md`。

| 层级 | 方案A 主张 | 项目007 裁决 | 判定 |
|---|---|---|---|
| 前端多端 | UniApp + Vue3 + TS | **Flutter 3.47 主干**（六端统一）+ RN 移动双端 | ❌ 不采用 |
| PC 客户端 | Electron + Vue3 | **Tauri 2**（Rust，体积小、无 Chromium 捆绑） | ❌ 不采用 |
| Web 端 | （未单列） | **Vite 6 + React 18 + TS 5.7** → 纯静态部署 | ✅ 现状为准 |
| 后端层 | Node.js + NestJS + TS | **Python + FastAPI**（`server/app`） | ❌ 不采用 |
| 数据层 | MySQL 8.0 + Redis 7.0 | **SQLite（`server/data/manju.db`）→ JSON 静态产物**；Serverless 无长驻中间件 | ❌ 不采用 |
| 部署运维 | Docker + 可视化面板 | **EdgeOne Makers**（`outputDirectory: static`）+ 云函数 | ❌ 不采用 |
| 接口规范 | RESTful + Swagger | **`spec/openapi.yaml` 契约先行**，四端模型由它派生 | ✅ 等效采用 |
| OTA 协议 | （未涉及） | `spec/ota-protocol.v1.md` + Ed25519 | ➕ 项目特有 |

> ⚠️ **由此产生的方案A 章节失效点**（务必按此读原文）：
> - 原文「阶段2 后端开发」中的 MySQL/Redis 设计工作 → 项目007 不存在，替换为「契约与静态导出链路重构」。
> - 原文「运维部署外包」→ 项目007 为 Serverless，无服务器可运维，该项**整体删除**。
> - 原文「阶段5 上线发布」的服务器/域名配置 → 项目007 需在**正式域名 + ICP 备案**就绪后才成立（见 `docs/blockers.md`）。

## 2. 落地节奏：四期路线 × 方案A 六阶段

方案A 的六阶段是**活动类型**（筹备/后端/前端/联调/上线/运维），
项目007 的四期是**交付批次**。二者是交叉关系，不是替代关系——下表给出映射。

| 方案A 阶段 | 项目007 对应期 | 自主（自己） | 外包并行 | 评审节点 | 门禁命令 |
|---|---|---|---|---|---|
| ① 筹备期 | 第一期前 + 第二期前 | 契约 `spec/openapi.yaml`、内容源白名单、正式域名备案 | 需求文档优化、UI/UX（T3）、品牌图标（T2） | **需求评审 + 技术方案评审** | `npm run typecheck` |
| ② 后端开发 | **第二期** | 去 sqlalchemy 依赖、OTA 路由与签名服务抽离、单测 | 非核心 CRUD、运维脚本（T7） | 技术方案 + 代码评审 | `python scripts/smoke_test.py` |
| ③ 前端多端开发 | **第一期**（Web）+ **第三期**（Flutter）+ **第四期**（Tauri/RN） | 核心页面、播放器、平台差异化适配（iOS/鸿蒙跳商店） | 纯展示页、鸿蒙验签补全（T1）、上架素材（T6） | 代码 + 交互体验评审 | `node makers/scripts/smoke_web.mjs` |
| ④ 联调与测试 | 每期收尾 | 前后端联调、核心流程验证、Bug 修复 | 兼容性测试 + 众测（T4）、安全扫描（T8） | **测试验收评审 + 灰度评审** | `node makers/scripts/verify_online_playback.mjs` |

## 3. 自动化评审门禁（方案A「自动化工具」一环的真实落地）

方案A 每个评审节点都要求「外部人员 + 自动化工具 + 用户」三方参与。
自动化那一环此前只存在于文档的命令表格里，**本轮接入 CI**：

`.github/workflows/review-gates.yml`（PR / push 触发，四个 job 并行）

| Job | 覆盖 | 判据 | 门槛 |
|---|---|---|---|
| `web-quality` | `npm ci` → `tsc --noEmit` → `vite build` → `smoke_web.mjs` | smoke_web 21/21 | 🔴 Hard |
| `backend-quality` | 安装依赖 → 启动 uvicorn → `smoke_test.py` | 19/19 | 🟡 Soft（`continue-on-error`，二期完成后转 Hard） |
| `security-gates` | `check_ota_keys.py` + 私钥泄露扫描 + 过期域名扫描 + 红线 rewrite 扫描 | 无命中 | 🔴 Hard |
| `contract-guard` | `spec/` 是否被改动、`edgeone.json` 红线 rewrite | 无违规 | 🔴 Hard |

> 线上真机判据（`verify_online_playback.mjs`）**不进 CI**——它依赖 EdgeOne 预览域的 SSO token，
> 约 3 小时过期，无法自动化。仍按 `docs/重建计划.md` 第五节要求**每次部署后手工跑**。

## 5. 使用方式（三步走）

1. **每期开工前**：复制 `review/01`、`02` 模板 → 按 `评审体系落地清单` 的检查项逐条填 → 准出后开工。
2. **每个 PR**：CI 自动跑四个 gate；人工按 `评审体系落地清单` §3.2 的 8 条必查项复核，填 `03`。
3. **每期收尾**：填 `04`（测试验收）；**仅第四期上线前**追加 `05`（合规），全项通过才提审。

### 5.1 扩展机制使用原则（2026-10-03 追加）

- 五类扩展机制只做**机检前置**；**准出判据唯一**＝CI 门禁 + `review/` 记录，专家/子代理意见不作为准出依据。
- 按阶段启用，不用即关（避免上下文膨胀）；新增前先确认风险台账 R-12 / R-13 / R-18。
- 部署一律走 EdgeOne Makers 连接器（本项目部署最高优先级通道）。
