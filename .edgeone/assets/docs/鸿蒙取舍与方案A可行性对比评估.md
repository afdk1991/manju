## 0. ⚠️ 先修正一处前次结论（重要）

本文档初稿曾判断「**方案A 的 UniApp + Electron 无法覆盖鸿蒙**」。经 2026-10-01 检索核实，
**该判断不准确，特此修正**：

| 事实 | 核实结果 |
|---|---|
| UniApp 对 HarmonyOS NEXT 的支持 | ✅ **已支持**。HBuilderX 4.24+ 可运行到鸿蒙；**4.27+ 正式支持 Harmony NEXT App 开发**；`uni-app x` 4.61+ 支持鸿蒙（要求 API 14+，uni-app 要求 API 12+） |
| 成熟度 | 2026 年公开资料称其为"前端跨端框架中鸿蒙生态适配最完整、落地最成熟"的方案 |
| 限制 | 逻辑层自 4.31 起迁至 **JSVM**，**无法在 JS 层直接调用鸿蒙原生接口**，所有原生交互须经 **UTS 插件中转**；复杂本地加密或高频渲染存在通信损耗 |

**因此，"能否覆盖鸿蒙"不再是方案A 的否决理由。** 真正的否决理由在下文第 3、4 节（已有资产作废 + Ed25519 验签走 UTS 中转的性能与复杂度代价）。

## 2. 六端覆盖矩阵（三方案横评）

| 端 | 现方案（Flutter 主干 + Tauri/RN 备选） | 方案A（UniApp + Electron） | 说明 |
|---|---|---|---|
| Android | ✅ Flutter / RN | ✅ UniApp / uni-app x | 持平 |
| iOS | ✅ Flutter / RN | ✅ UniApp / uni-app x | 持平；两端均**禁止静默安装**，只能跳商店 |
| **HarmonyOS** | ✅ Flutter OHOS 分支 + **原生 ArkTS 已实现** | ✅ **UniApp（4.27+/x 4.61+）亦支持** | **修正后持平**；但见下方差异 |
| Windows | ✅ Flutter / Tauri 2 | ✅ Electron | 持平 |
| macOS | ✅ Flutter / Tauri 2 | ✅ Electron | 持平；两端均需 Developer ID 签名 |
| Linux | ✅ Flutter / Tauri 2 | ✅ Electron（支持） | 持平 |
| 小程序 | ❌ 不支持 | ✅ UniApp 强项（10+ 平台） | **方案A 唯一实质优势** |

**关键差异（鸿蒙端）**：

| 维度 | 现方案（原生 ArkTS） | 方案A（UniApp） |
|---|---|---|
| 代码现状 | `clients/manju_rn/harmony/.../Index.ets`、`updater/Updater.ets`；`clients/manju_flutter/ohos/.../Index.ets`、`UpdaterPlugin.ets` **均已实现** | 需全部重写为 Vue3 + UTS 插件 |
| **Ed25519 / SHA256 验签** | 可直接在 ArkTS 用 `cryptoFramework` 实现（当前**尚未实现**，是待补缺口） | JSVM 逻辑层**无法直接调用原生接口**，须经 **UTS 插件中转**；公开资料明确指出"复杂本地加密"存在通信损耗风险 |
| 工具链 | DevEco Studio（你尚未安装） | DevEco 5.0.3.400+ / 5.0.7.100+ **同样需要** |
| 系统版本要求 | 由 Flutter OHOS 分支决定 | uni-app 需 API 12+；uni-app x 需 API 14+ |

## 4. 方案A 唯一的实质优势（应单独评估，不必整套换栈）

**小程序端覆盖**（微信 / 支付宝 / 抖音等 10+ 平台）——这是现方案完全不具备的能力。

若业务确实需要小程序，**推荐做法是增量引入，而非替换主干**：

| 做法 | 说明 |
|---|---|
| ✅ 增量：新增小程序端（UniApp / Taro），复用同一份 `spec/openapi.yaml` 契约 | 不动 Flutter 主干与后端，风险可控 |
| ❌ 替换：整套转 UniApp | 上文第 3 节全部代价 |

> 判断依据：项目007 的 `spec/openapi.yaml` 已是"契约先行"的唯一事实源，
> 小程序端只要按契约实现即可接入，不需要动客户端主干。

## 5. 什么情况下才应改用方案A（触发条件）

同时满足以下**全部**条件时，才值得重新评估路线 B：

1. 业务重心转向**小程序**为主、原生 App 为辅（此时 UniApp 的端到端效率优势才成立）
2. 愿意接受**已建成的 OTA v1 / Ed25519 / 19 项冒烟全部作废**
3. 能承担首年 8500~23000 元成本（当前为 0）
4. 已有或愿意部署 MySQL 8.0 + Redis 7.0 环境
5. 愿意推翻 `docs/重建计划.md` 中 2026-10-01 已确认的分期决策

**当前状态：5 条全部不满足。** → 维持路线 A。

## 6. 鸿蒙端的现实处理建议（不取舍，分阶段）

| 阶段 | 动作 | 依据 |
|---|---|---|
| 近期 | **补齐鸿蒙验签**（外包 T1，800~2000 元）：`Updater.ets:36` 目前只有 `signature?: string` 声明、无实现；`UpdaterPlugin.ets` 同样缺失 | `docs/blockers.md` 第 5 节问题 4 |
| 近期 | 先确认 `cryptoFramework` 的 **Ed25519** 支持情况；若不支持，降级方案为 **SHA256 校验 + HTTPS 缓解**（鸿蒙只能跳 AppGallery，风险限于跳转 URL 篡改） | blockers.md 第 5 节 |
| 中期 | 补齐 DevEco 环境后做鸿蒙真机验证（当前🟡 从未验证） | blockers.md 第 4 节 |
| 长期 | 若鸿蒙用户量占比长期 <5%，可考虑**降为仅维护**，但不因"改写技术栈"而放弃 | 数据驱动决策 |

> **不建议**因为"验签没实现 + 只能跳商店"就砍掉鸿蒙端：
> 这两点都是**可修复的缺口**，而非架构性缺陷；且鸿蒙端代码已存在，边际成本很低。
